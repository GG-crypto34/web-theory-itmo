1Метафреймворки: назначение и отличия от обычных фреймворков

UI-фреймворк умеет рисовать компоненты. Метафреймворк добавляет вокруг него всё остальное приложение: сервер, маршруты, данные, сборку.

Определение. Метафреймворк - фреймворк поверх UI-фреймворка, который даёт готовую архитектуру full-stack приложения: файловую маршрутизацию, серверный рендеринг, загрузку данных на сервере, кеш, middleware, серверные обработчики и сборку для продакшена.

В нашем коде. Next.js 16.4 с App Router, JavaScript без TypeScript. Java-бэкенд из ЛР 3-4 не менялся: вся бизнес-логика, проверка паролей и база остаются там, а сервер Next только рендерит страницы и ходит в API.
Вопрос: Одной фразой: что такое метафреймворк?
Ответ: Надстройка над UI-фреймворком, которая даёт маршруты по файлам, серверный рендеринг, загрузку данных, кеш, middleware и сборку - то есть готовое приложение, а не только компоненты.
Вопрос: Next.js - это backend?
Ответ: У него есть серверная часть, но у нас она - "backend for frontend": только рендер, маршрутизация, middleware и получение данных. Бизнес-логика и БД в Java.

2Ограничения SPA. Клиентский и серверный рендеринг

SPA быстрая после загрузки, но первый экран ждёт и JavaScript, и данные.

Определение. CSR (Client-Side Rendering) - сервер отдаёт пустой HTML и бандл JS; браузер выполняет JS, запрашивает данные и строит интерфейс. Так работала ЛР 4.
Определение. SSR (Server-Side Rendering) - на каждый запрос сервер выполняет компоненты, получает данные и отдаёт готовый HTML. Потом браузер загружает JS и гидратирует страницу.
CSR:  HTML(пустой) -> JS -> выполнение -> запрос данных -> рендер   (контент в самом конце)
SSR:  запрос -> сервер: данные + рендер -> HTML с контентом -> JS -> гидратация
ограничение SPAпочему
медленный первый экрансначала скачать и выполнить весь JS, потом ещё запрос данных
плохо для SEO и превью ссылокробот видит пустой <div id="root">
большой бандлвесь код интерфейса едет в браузер
нагрузка на слабые устройствавесь рендер на клиенте
мигание интерфейса"гость" -> "пользователь", пока восстанавливается сессия
Определение. Метрики. TTFB - время до первого байта ответа. FCP - первая отрисовка контента. LCP - отрисовка самого большого элемента. INP - задержка реакции на ввод. CLS - сдвиги вёрстки. LCP, INP и CLS - Core Web Vitals.

SSR улучшает FCP и LCP, но увеличивает TTFB (сервер ждёт данные) и нагружает сервер. Медленный бэкенд SSR не ускорит; для этого есть стриминг и кеш.

В нашем коде. Открой /students и посмотри исходный код (Ctrl+U): таблица студентов уже в HTML. В ЛР 4 там был пустой <div id="root">. Шапка сразу показывает логин и роль, без мигания: layout.jsx читает сессию из cookie на сервере.
Вопрос: Почему SSR может ухудшить TTFB?
Ответ: Сервер не может отправить первый байт, пока не получит данные и не отрендерит страницу. При CSR пустая оболочка отдаётся мгновенно.

3Стратегии рендеринга: CSR, SSR, SSG, ISR

Главный вопрос: когда создаётся HTML - в браузере, на каждый запрос, при сборке или при сборке с периодическим обновлением.

стратегиякогда создаётся HTMLплюсыминусыкогда применять
CSRв браузередешёвый сервер, богатая интерактивностьмедленный первый экран, SEOзакрытые панели, редакторы
SSRна каждый запроссвежие и персональные данные, SEOнагрузка на сервер, TTFBличные кабинеты, поиск, фильтры
SSGпри сборке (next build)максимально быстро, раздаётся с CDNданные устаревают до пересборкидокументация, лендинги, блог
ISRпри сборке, потом пересоздаётся в фонескорость SSG + обновлениеданные могут быть устаревшими до revalidateкаталоги, новости
Определение. ISR (Incremental Static Regeneration) - статическая страница с временем жизни. По истечении revalidate первый посетитель получает старую версию, а сервер в фоне строит новую (stale-while-revalidate).

В Next стратегия выбирается автоматически: если страница использует запросо-зависимые данные (cookies(), headers(), searchParams), она динамическая (SSR); если нет - статическая (SSG).

В нашем коде. Все страницы динамические: next build помечает их значком ƒ (Dynamic). Причина - каждая страница персональна: читает cookie сессии, а список ещё и searchParams. SSG тут не подойдёт: студенты закрыты авторизацией и зависят от фильтров. Идею ISR мы используем на уровне данных: ответы Java кешируются на 30 секунд (вопрос 12).
Вопрос: Почему у вас нет SSG?
Ответ: Все данные закрыты логином и зависят от пользователя и фильтров. Статическая страница была бы одна на всех, а при сборке нет ни токена, ни параметров запроса.

4Гибридный рендеринг

Не "весь сайт SSR" или "весь сайт CSR", а своя стратегия для каждой страницы и даже для частей одной страницы.

Определение. Гибридный рендеринг - сочетание стратегий в одном приложении: одни маршруты статические, другие серверные; внутри страницы серверная разметка соседствует с интерактивными клиентскими "островами".

Уровни гибридности:

  1. по маршрутам: /about - SSG, /students - SSR;
  2. по компонентам: страница рендерится на сервере, а кнопки, формы и меню - клиентские компоненты, которые после гидратации работают как SPA;
  3. по времени: каркас страницы отправляется сразу, медленная часть догружается стримингом.
В нашем коде. Страница /students: серверная оболочка и таблица (StudentsTable - серверный компонент) + клиентские StudentFilters и StudentSearch (поиск с задержкой 300 мс, селекты сортировки). Переходы по ссылкам после загрузки - клиентские, как в SPA. Страница студента: серверная карточка + клиентская DeleteStudentButton с модальным окном.
Вопрос: Где у вас граница между сервером и клиентом на странице списка?
Ответ: page.jsx и StudentsTable рендерятся на сервере и ходят в Java. StudentFilters и StudentSearch помечены 'use client': они меняют URL через router.push, а сервер в ответ присылает новый рендер таблицы.

5Hydration: назначение и Hydration Mismatch

Сервер прислал "картинку" страницы; гидратация оживляет её: навешивает обработчики и подключает состояние.

Определение. Гидратация (hydration) - процесс, при котором React в браузере проходит по уже готовому серверному HTML, строит у себя то же дерево компонентов и привязывает к существующим DOM-узлам обработчики событий и состояние, не пересоздавая DOM.

Порядок: HTML пришёл и показан (страница видна, но кнопки ещё "мёртвые") -> загрузился JS -> hydrateRoot -> страница интерактивна. Между показом и гидратацией клик по кнопке ничего не делает - это одна из причин держать клиентский JS маленьким.

Определение. Hydration mismatch - разметка, которую React построил в браузере при гидратации, не совпала с серверным HTML. React выдаёт ошибку и перерисовывает расхождение на клиенте (теряется смысл SSR, возможно мигание).
типичная причинапочему разноекак избежать
Date.now(), Math.random() в рендересервер и браузер вызвали в разное времявычислить один раз на сервере и передать props
window, localStorage в рендерена сервере их нетчитать в useEffect или через useSyncExternalStore с серверным снимком
форматирование дат и чиселразная локаль и часовой поясявная локаль или формат на сервере
невалидная вложенность HTMLбраузер "чинит" <div> внутри <p>правильная разметка
расширения браузераменяют DOM до гидратацииsuppressHydrationWarning точечно
В нашем коде. Пользователь для шапки определяется на сервере (getSession() в layout.jsx) и передаётся в клиентский Navigation как prop - сервер и клиент рисуют одно и то же. Клиентские компоненты не читают window и время в рендере. Фильтры берут значения из URL через useSearchParams, который одинаков на сервере и в браузере. Даты выводятся строкой как пришли из API (2024-09-01), без локального форматирования.
Вопрос: Что будет, если в рендере написать {new Date().toLocaleTimeString()}?
Ответ: Сервер отрисует одно время, браузер при гидратации - другое: hydration mismatch. Время надо передать с сервера или показывать после монтирования в useEffect.

6Streaming SSR

Не ждать самую медленную часть: отправить готовое сразу, остальное дослать в том же ответе.

Определение. Streaming SSR - сервер отправляет HTML по частям через chunked-ответ. Сначала каркас страницы и заглушки (fallback) для медленных частей, затем, по мере готовности данных, - их HTML и маленький скрипт, который ставит его на место заглушки.

Границы стриминга задаёт <Suspense fallback={...}>: всё внутри может прийти позже. loading.jsx в Next - это автоматический Suspense вокруг всей страницы сегмента.

Плюсы: маленький TTFB и FCP даже при медленном API, части страницы не блокируют друг друга, гидратация тоже идёт по частям (selective hydration).

Ловушка. Как только первый кусок ушёл, HTTP-статус и заголовки уже отправлены. Если потом внутри Suspense вызвать notFound() или redirect(), статус останется 200: Next вставит в HTML meta-тег и сделает переход на клиенте.
В нашем коде. В app/students/page.jsx: 
<Suspense key={queryString(query)} fallback={<StudentsTableSkeleton />}>
  <StudentsTable query={query} />
</Suspense>
Заголовок, фильтры и поиск приходят сразу, на месте таблицы - скелет из плейсхолдеров Bootstrap; когда Java ответит, придёт настоящая таблица. key меняется вместе с фильтрами, поэтому при каждом новом поиске снова показывается скелет. Из-за ловушки выше на странице студента /students/[id] нет loading.jsx: иначе для несуществующего студента вернулся бы статус 200 вместо 404.
Вопрос: Чем стриминг отличается от загрузки таблицы через fetch в useEffect?
Ответ: Данные запрашивает сервер, а таблица приходит готовым HTML в том же HTTP-ответе. Не нужен JS, второго запроса из браузера нет, а при отключённом JS таблица всё равно появится.

7Серверные и клиентские компоненты

В App Router каждый компонент по умолчанию серверный. Клиентским он становится только с директивой 'use client'.

серверный компонент (RSC)клиентский компонент
где выполняетсятолько на серверена сервере для первого HTML и в браузере (гидратация, обновления)
JS в браузерне отправляетсяотправляется
можетasync/await, читать cookie, ходить в API и БД, использовать секретыuseState, useEffect, обработчики событий, window
не можетхуки состояния, обработчики, браузерные APIбыть async, читать серверные секреты

Правила границы:

  • 'use client' ставится в начале файла и делает клиентским этот модуль и всё, что он импортирует;
  • серверный компонент может рендерить клиентский и передавать ему сериализуемые props (строки, числа, объекты, server actions), но не обычные функции и не компоненты;
  • клиентский может получать серверный как children;
  • пакет server-only: импорт такого модуля из клиентского кода ломает сборку - защита от утечки серверного кода.
Определение. Server Action ('use server') - асинхронная функция, которая выполняется на сервере, но вызывается из клиентского кода как обычная функция. Под капотом браузер делает POST-запрос.
В нашем коде.
Серверные: все page.jsx, layout.jsx, StudentsTable, RoleBadge, Forbidden.
Клиентские: Navigation (меню-бургер), LoginForm, RegisterForm, StudentForm, StudentFilters, StudentSearch, DeleteStudentButton, LogoutButton, error.jsx.
lib/backend.js, session.js, students.js начинаются с import 'server-only': адрес Java и токены никогда не попадут в браузерный бандл.
Server actions в lib/actions/auth.js и lib/actions/students.js. В edit/page.jsx серверная страница передаёт клиентской форме action через updateStudentAction.bind(null, id).
Компоненты react-bootstrap с точкой (Card.Header) используются только в клиентских файлах: из серверного компонента нельзя обращаться к свойствам клиентского модуля, поэтому на сервере вёрстка сделана классами Bootstrap.
Вопрос: Почему Navigation клиентский, а RoleBadge нет?
Ответ: Navigation использует usePathname (подсветка активной ссылки) и раскрывающееся меню на телефоне - это состояние и события. RoleBadge просто рисует span по props, ему JS в браузере не нужен.
Вопрос: Можно ли из серверного компонента передать в клиентский onClick={() => ...}?
Ответ: Нет, обычная функция не сериализуется. Можно передать server action или перенести обработчик внутрь клиентского компонента.

Вопрос: Что будет с layout при переходе с /students на /students/123456?
Ответ: Корневой layout не перемонтируется и сохраняет состояние (шапку); меняется только содержимое children. Это главное отличие layout от простого компонента-обёртки на каждой странице.

9Клиентская навигация и prefetching

Первый заход - SSR, дальнейшие переходы - как в SPA, только данные приходят уже отрендеренными.

Клик по <Link> не перезагружает документ. Роутер Next запрашивает у сервера RSC payload нового маршрута (сериализованное дерево серверных компонентов, а не HTML) и аккуратно вливает его в текущую страницу: общий layout и состояние клиентских компонентов сохраняются.

Определение. Prefetching - предварительная загрузка следующей страницы до клика. <Link> в продакшене подгружает маршрут, когда ссылка появляется в области видимости; для динамических страниц заранее грузится их статическая часть до ближайшего loading.jsx. Программно: router.prefetch(href).

Плюс: переход ощущается мгновенным. Минус: лишний трафик, поэтому для длинных списков ссылок prefetch можно отключить prefetch={false}.

способкогда
<Link href>обычные ссылки
router.push / replaceпереход из кода (после действия)
router.refresh()перезапросить серверный рендер текущей страницы
redirect()на сервере: в компоненте, server action, route handler
В нашем коде. Все внутренние ссылки - next/link: ФИО в таблице, пагинация, кнопки "К списку". Фильтры и сортировка меняют URL через router.push внутри startTransition (хук useStudentsQuery): пока сервер готовит ответ, старая таблица остаётся на экране, а кнопка "Найти" показывает спиннер. Поиск по ФИО использует router.replace, чтобы каждая буква не попадала в историю браузера.
Вопрос: Что передаётся по сети при клиентском переходе в App Router?
Ответ: Не HTML и не JSON API, а RSC payload: сериализованный результат рендера серверных компонентов со ссылками на клиентские компоненты. Роутер применяет его к текущему дереву.

10Серверная загрузка данных. Взаимодействие с внешним REST API

Серверный компонент - async-функция: await данные и сразу верни разметку. Ни useEffect, ни состояний loading.

export default async function ProfilePage() {
  const user = await readAuthorized((token) =>
    backendFetch('/api/auth/session/me', { token }));
  return <ul>...{user.email}...</ul>;
}

Почему это лучше, чем запрос из браузера:

  • сервер Next обычно рядом с API (одна docker-сеть) - запросы быстрые;
  • токены и адрес API не попадают в браузер;
  • нет CORS: запрос сервер-сервер;
  • ответ можно кешировать для всех запросов (Data Cache).
В нашем коде.
lib/backend.js - функция backendFetch: адрес из переменной окружения API_URL (в Docker http://backend:8080), заголовок Authorization: Bearer, таймаут 15 с через AbortSignal.timeout, ошибки Java { error: { code, message, details } } превращаются в ApiError.
lib/students.js - listStudents и getStudent: валидация параметров (searchDto из домена ЛР 4), кеш, проверка ответа (pageFromDto, studentFromDto).
Изменения идут через server actions (createStudentAction, updateStudentAction, deleteStudentAction): они вызывают POST, PATCH, DELETE в Java и проверяют роль.
Браузер вообще не знает адрес Java: порт 8080 в compose оставлен только для Swagger.
Вопрос: Где у вас хранится адрес бэкенда и почему он не в браузере?
Ответ: В переменной окружения API_URL, читается в lib/config.js и используется только в server-only модулях. Браузер общается лишь с Next; в бандл адрес не попадает.

11Последовательная и параллельная загрузка. Request Waterfall

Определение. Request waterfall (водопад запросов) - запросы выполняются друг за другом, хотя могли бы идти одновременно. Общее время = сумма, а не максимум.
// водопад: 300 + 300 = 600 мс
const student = await getStudent(id);
const history = await getHistory(id);

// параллельно: max(300, 300) = 300 мс
const [student, history] = await Promise.all([getStudent(id), getHistory(id)]);

Последовательно надо только когда второй запрос зависит от результата первого. Типичные источники водопада: await подряд; вложенные компоненты, каждый из которых ждёт свои данные; в SPA - загрузка JS, потом запрос данных, потом ещё запрос по результату.

Способы борьбы:

  • Promise.all для независимых запросов;
  • начать запрос раньше (preload), а await сделать позже;
  • разнести по разным <Suspense>, чтобы части не ждали друг друга;
  • дедупликация: одинаковый запрос в разных компонентах выполнить один раз (cache() React, мемоизация fetch в Next).
В нашем коде.
loadStudent обёрнут в cache() из React: его вызывают и generateMetadata, и сама страница, но запрос в Java уходит один раз.
getSession тоже в cache(): layout и страница не разбирают cookie дважды.
На странице списка медленная часть (таблица) вынесена в Suspense, поэтому каркас страницы не ждёт Java.
По-настоящему зависимые шаги идут последовательно: сначала proxy обновляет токен, потом рендер с этим токеном.
Вопрос: Как найти водопад?
Ответ: Во вкладке Network (или в логах сервера) запросы идут "лесенкой": следующий стартует, когда закончился предыдущий, хотя от него не зависит.

12Кеширование данных. Cache Hit, Cache Miss и стратегии

Определение. Cache hit - нужные данные нашлись в кеше и отданы без обращения к источнику. Cache miss - в кеше нет (или устарело), идём к источнику и обычно сохраняем результат.
стратегиясуть
cache-aside (lazy)при miss загрузить и положить в кеш; самая частая
TTLзапись живёт заданное время
stale-while-revalidateотдать устаревшее сразу, обновить в фоне
write-throughпри записи обновить и источник, и кеш
инвалидация по событиюпосле изменения пометить кеш устаревшим

Уровни кеша в Next:

кешгдечто хранит
Request memoizationсервер, в пределах одного рендераодинаковые fetch и функции в cache()
Data Cacheсервер, между запросамиответы fetch с cache: 'force-cache'
Full Route Cacheсерверготовый HTML статических страниц
Router CacheбраузерRSC payload посещённых и prefetch-нутых страниц

В Next 15-16 fetch по умолчанию не кешируется, кеш включают явно.

В нашем коде (lib/students.js): 
fetch(url, {
  cache: 'force-cache',
  next: { tags: ['students'], revalidate: 30 },   // 30 из STUDENTS_REVALIDATE
});
Повторное открытие той же страницы с теми же фильтрами в течение 30 секунд - cache hit, Java не дёргается. Другие фильтры, другая страница или прошло 30 с - miss.
Безопасность. Ключ кеша Next строится из URL, метода и заголовков, в том числе Authorization. Поэтому у каждого токена свои записи: подделанный или чужой токен не получит данные из кеша, будет miss, и Java ответит 401. Мы это проверили: с поддельным токеном данных в HTML нет. Профиль (/session/me) не кешируется вообще (no-store).
Вопрос: Почему бы не кешировать список один на всех пользователей?
Ответ: Тогда данные отдавались бы без проверки токена бэкендом: Next не проверяет подпись JWT. Любой с поддельной cookie получил бы список из кеша. С токеном в ключе каждый miss проходит через Java.

13Revalidation и инвалидация кеша

Определение. Revalidation - обновление закешированных данных. По времени: запись устаревает через N секунд. По событию (on-demand): код явно говорит "эти данные изменились".
API Next 16что делаетгде можно
next: { revalidate: N }устаревание через N секунд, обновление по stale-while-revalidateв fetch
next: { tags: [...] }метки записи для точечного сбросав fetch
updateTag(tag)сразу просрочить; следующий запрос ждёт свежие данные (read-your-own-writes)только server actions
revalidateTag(tag, 'max')пометить устаревшим; отдаётся старое, обновляется в фонеserver actions, route handlers
revalidatePath(path)сбросить всё для путиserver actions, route handlers

По времени - просто, но данные могут быть устаревшими до N секунд и сбрасываются, даже если ничего не менялось. По событию - точно, но нужно знать все места изменений. Обычно сочетают: событие для своих изменений, время как страховка от чужих.

В нашем коде. Оба способа.
По времени: revalidate: 30 - изменения, сделанные мимо нашего фронта (через Swagger или другим админом), появятся максимум через 30 секунд.
По событию: в lib/actions/students.js после успешного POST, PATCH или DELETE: 
updateTag('students');            // все списки
updateTag(`student-${isuId}`);    // карточка этого студента
updateTag, а не revalidateTag, потому что после сохранения нас сразу ведут на карточку или список, и там должны быть уже новые данные, а не старые из фона. Проверено: после изменения комнаты отфильтрованный список сразу показывает новое значение.
Вопрос: Чем updateTag отличается от revalidateTag?
Ответ: updateTag сразу удаляет запись, и следующий запрос ждёт свежие данные - пользователь видит своё изменение. revalidateTag с профилем 'max' отдаёт старое и обновляет в фоне. updateTag доступен только в server actions.

14Middleware и защищённые маршруты

Middleware срабатывает на сервере до рендера страницы и может пропустить, перенаправить, переписать запрос или поменять cookie.

Важно для защиты. В Next 16 файл middleware.js переименован в proxy.js, функция - proxy. Работает так же; старое имя объявлено устаревшим.
// src/proxy.js
export async function proxy(request) {
  const access = request.cookies.get('lab5_access')?.value;
  if (isAccessFresh(access)) return NextResponse.next();       // пропустить
  const pair = await refreshTokens(request.cookies.get('lab5_refresh')?.value);
  if (!pair) return toLogin(request);                          // на /login?next=...
  // новые cookie: и в ответ браузеру, и в текущий запрос для рендера
  ...
}
export const config = { matcher: ['/students/:path*', '/profile/:path*'] };

Как устроена авторизация

  1. Вход: server action loginAction вызывает Java POST /api/auth/login и кладёт оба токена в cookie lab5_access и lab5_refresh (HttpOnly, SameSite=Lax, Secure по настройке).
  2. Каждый переход на защищённую страницу проходит через proxy: нет сессии - редирект на вход с параметром next; access скоро истечёт (меньше 30 с) - обмен refresh на новую пару.
  3. Страница ещё раз проверяет сессию (requireSession): proxy не должен быть единственной защитой, его покрытие зависит от matcher.
  4. Server action проверяет роль сам (requireAdmin), при 401 обновляет токены и повторяет (actAuthorized).
  5. Последняя линия - Java проверяет подпись и роль.
Ловушка. Proxy и Next не проверяют подпись JWT, только читают срок и роль. Поэтому никакие данные не отдаются без запроса в Java с этим токеном.
В нашем коде. Только админу: /students/new и /students/[id]/edit показывают USER-у "у миня нет прав" (Forbidden.jsx), кнопки изменения и удаления не рендерятся. Если Java ответит 401 во время рендера (cookie там менять нельзя), страница уводит на route handler /session-expired, который удаляет cookie и редиректит на вход. Параметр next проверяется safeNext: только пути внутри сайта, защита от open redirect.
Вопрос: Почему токены в cookie, а не в памяти браузера, как в ЛР 4?
Ответ: Рендер идёт на сервере: серверу нужен токен, чтобы сходить в Java. Память браузера ему недоступна, а cookie браузер присылает с каждым запросом. HttpOnly не даёт прочитать её из JS.
Вопрос: Чем защищены server actions от CSRF?
Ответ: Next принимает их только POST-ом и сверяет заголовок Origin с Host; плюс cookie SameSite=Lax не уходят с POST-запросами с чужих сайтов.

В нашем коде.

Прочее: страница за пределами списка (после удаления последнего студента на странице) - redirect на последнюю существующую; ошибки форм - сообщения из getErrorMessage по коду ошибки Java.
Вопрос: Почему error.jsx обязан быть клиентским?
Ответ: Это React Error Boundary, а ему нужно состояние и функция reset для повторной попытки в браузере. Серверные компоненты состояния не имеют.
Вопрос: Почему с loading.jsx несуществующий студент отдал бы 200?
Ответ: loading.jsx включает стриминг: заголовки со статусом 200 уходят сразу вместе со спиннером, а notFound() вызывается позже, когда статус уже не изменить.

Шпаргалка к защите

Вопрос: Расскажи про ЛР 5 за минуту.
Ответ: Фронт из ЛР 4 перенесён на Next.js 16 App Router. Страницы рендерятся на сервере, Next ходит в Java-API с токеном из HttpOnly cookie. proxy.js (бывший middleware) не пускает без сессии и обновляет токен. Студенты кешируются в Data Cache с тегами и сроком 30 с, после изменений кеш сбрасывается updateTag. Есть Suspense-стриминг таблицы, error.jsx, not-found с честным 404. Docker: Postgres, Java и Next в режиме standalone.
Вопрос: CSR против SSR?
Ответ: CSR: пустой HTML, всё строит браузер после загрузки JS и данных. SSR: сервер отдаёт HTML с данными, браузер его гидратирует. SSR быстрее показывает контент и лучше для SEO, но нагружает сервер и увеличивает TTFB.
Вопрос: Что такое гидратация?
Ответ: React в браузере проходит по серверному HTML, строит то же дерево и подключает обработчики и состояние к существующим DOM-узлам. Mismatch - когда клиентский рендер не совпал с серверным.
Вопрос: Как устроен кеш и как он обновляется?
Ответ: fetch с cache: 'force-cache', теги students и student-ID, revalidate 30 секунд. После create, update, delete server action вызывает updateTag, и следующий рендер берёт свежие данные. Ключ включает Authorization, поэтому кеш свой у каждого токена.
Вопрос: Где middleware и что он делает?
Ответ: src/proxy.js, в Next 16 middleware называется proxy. На /students и /profile: свежий access - пропуск; нет - обмен refresh на новую пару с записью cookie; не вышло - редирект на /login?next=...
Вопрос: Как устроены роли?
Ответ: Роль из JWT. Интерфейс прячет кнопки, страницы new и edit показывают "нет прав", server actions проверяют requireAdmin, а Java всё равно проверяет роль и вернёт 403.
Вопрос: Что изменилось в Docker по сравнению с ЛР 4?
Ответ: Вместо nginx со статикой - Node-сервер Next: output: 'standalone' собирает минимальный server.js, многоэтапная сборка deps, build, runtime, запуск от пользователя node. В compose фронт получает API_URL=http://backend:8080 и публикуется на 8081.
