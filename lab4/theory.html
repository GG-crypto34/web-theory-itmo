1JavaScript-фреймворки: React, Vue, Angular, Svelte

Фреймворк берёт на себя синхронизацию данных и DOM. Мы описываем, как интерфейс должен выглядеть при данном состоянии, а не как его менять.

Зачем нужен фреймворк

На чистом JS (как в ЛР 1) каждое изменение данных надо вручную переносить в DOM: найти элемент, поменять текст, добавить строку таблицы, не забыть убрать старую. Чем больше экранов и состояний, тем больше таких мест и тем легче ошибиться. Фреймворк даёт:

  • декларативный UI: интерфейс описывается как функция от состояния;
  • компоненты: интерфейс собирается из независимых переиспользуемых частей;
  • реактивность: при изменении данных нужные части перерисовываются сами;
  • экосистему: роутер, сторы, сборщик, devtools.

Почему у нас React

Это вариант задания. React даёт JSX, хуки и огромную экосистему: react-router-dom для маршрутов, zustand для глобального состояния, react-bootstrap для вёрстки. Сборка через Vite.

В нашем коде. Точка входа src/main.jsx: createRoot(...).render(<AuthProvider><App /></AuthProvider>) внутри StrictMode. Маршруты описаны в src/App.jsx.
Вопрос: React - это фреймворк или библиотека?
Ответ: Формально библиотека для построения UI: она отвечает только за компоненты и рендер. Маршрутизацию, состояние, запросы добавляют отдельные пакеты. Angular, наоборот, даёт всё сразу.
Вопрос: Чем Svelte принципиально отличается от React?
Ответ: Svelte - компилятор: на этапе сборки превращает компоненты в код, который точечно меняет DOM. В рантайме нет Virtual DOM и сравнения деревьев.

2SPA и клиентская маршрутизация

Одна HTML-страница, а "переходы" между экранами делает JavaScript без перезагрузки документа.

Определение. SPA (Single Page Application) - приложение, которое загружает один HTML-документ и дальше меняет его содержимое через JS. Данные приходят с сервера в JSON через REST API.
Определение. MPA (Multi Page Application) - классический сайт: каждый переход запрашивает у сервера новую HTML-страницу целиком.
SPAMPA
быстрые переходы, состояние не теряетсякаждый переход - полная перезагрузка
медленный первый заход (надо скачать JS)первый экран сразу готов
HTML пустой: плохо для SEOHTML с контентом
сервер отдаёт только JSONсервер рендерит страницы

Как работает клиентская маршрутизация

  1. Роутер перехватывает клик по ссылке (<Link>) и отменяет обычный переход браузера.
  2. Меняет адрес через History API: history.pushState(). Страница не перезагружается.
  3. Сопоставляет новый путь с таблицей маршрутов и рендерит нужный компонент.
  4. Кнопки "назад/вперёд" вызывают событие popstate, роутер снова выбирает компонент.

Параметры пути (/students/:isuId) роутер достаёт и отдаёт компоненту через useParams().

Запасной index.html на сервере

Если пользователь обновит страницу на /students/123456, браузер спросит у сервера именно этот путь. Файла с таким именем нет, поэтому сервер должен на любой неизвестный путь отдавать index.html, а дальше маршрут разберёт роутер в браузере.

В нашем коде. BrowserRouter и Routes в App.jsx; / перенаправляет на /login через <Navigate>, путь * показывает "страница куда-то делась". На сервере это строка try_files $uri $uri/ /index.html; в nginx.conf.
Вопрос: Почему после F5 на /students/5 без настройки nginx будет 404?
Ответ: Браузер запросит у сервера файл по этому пути, а его нет. Маршрут существует только в JS-роутере. Нужен fallback на index.html (try_files).
Вопрос: Чем <Link> отличается от <a href>?
Ответ: <a> делает полную перезагрузку страницы и теряет состояние. Link перехватывает клик и меняет адрес через History API, перерисовывая только нужные компоненты.

3Компонентная архитектура: компоненты, props, события

Компонент - функция, которая получает данные и возвращает разметку.

Определение. Компонент - независимая часть интерфейса со своей разметкой, логикой и состоянием. В React это функция, возвращающая JSX.
Определение. Props - входные параметры компонента. Передаются от родителя к ребёнку и внутри ребёнка только читаются.

Данные в React текут сверху вниз (one-way data flow). Ребёнок не может изменить данные родителя напрямую. Чтобы сообщить наверх о событии, родитель передаёт ребёнку функцию-колбэк, а ребёнок её вызывает. Это и есть "события" между компонентами.

// родитель                                  // ребёнок
<StudentFilters                              function StudentFilters({ onApply }) {
  onNameChange={handleNameChange}              ...
  onApply={handleApply} />                    onApply(filters);  // событие наверх
                                             }

Для общих данных далеко по дереву используют Context или глобальный стор, чтобы не "пробрасывать" props через много уровней (prop drilling).

children - специальный prop: то, что лежит между тегами компонента. Аналог слотов во Vue.

В нашем коде. StudentForm получает student, onSubmit, submitting, buttonText и используется и для создания, и для редактирования. ProtectedRoute принимает children и флаг adminOnly. StudentFilters сообщает наверх через onApply и onNameChange.
Вопрос: Можно ли изменить prop внутри компонента?
Ответ: Нет, props только для чтения. Если значение должно меняться, это состояние: либо локальное (useState), либо его хранит родитель и даёт колбэк для изменения.
Вопрос: Что такое prop drilling?
Ответ: Передача props через промежуточные компоненты, которым эти данные не нужны, только чтобы донести их вглубь. Решается Context или глобальным стором (у нас zustand для сессии).

4Жизненный цикл компонентов и хуки

Монтирование, обновления, размонтирование. В функциональных компонентах всё это выражается хуками.

Этапы жизни

  1. Монтирование: компонент впервые попал в дерево, его DOM вставлен на страницу.
  2. Обновление: изменились props или состояние, компонент перерисовался.
  3. Размонтирование: компонент убран из дерева; нужно отписаться от всего, на что подписались.

Хуки

хукзачем

useEffectпобочные эффекты после рендера: подписки, запросы, таймеры
useMemoзапомнить вычисленное значение между рендерами
useCallbackзапомнить функцию
useRefизменяемое значение без перерисовки, ссылка на DOM
useContextпрочитать значение из Context
свои хукифункции useXxx, которые объединяют другие хуки

useEffect и cleanup

useEffect(() => {
  const subscription = events$.subscribe(handle);   // при монтировании или смене key
  return () => subscription.unsubscribe();           // cleanup: перед следующим запуском и при размонтировании
}, [key]);                                          // зависимости
  • без массива зависимостей: после каждого рендера;
  • []: один раз после монтирования;
  • [a, b]: когда изменились a или b.
Ловушка. Правила хуков: вызывать только на верхнем уровне компонента или своего хука, не внутри if и циклов. React узнаёт хуки по порядку вызова. У нас это проверяет линтер правилом react/rules-of-hooks.
Ловушка. В режиме разработки StrictMode специально монтирует компонент дважды (mount, unmount, mount), чтобы проверить, что cleanup написан правильно.
В нашем коде. Свои хуки useStudentList, useStudent, useStudentResource. В useStudentResource эффект подписывается на RxJS-поток и в cleanup делает unsubscribe() и removeResource(key). В EditStudentPage эффект создаёт AbortController и отменяет запрос при уходе со страницы. AuthProvider один раз при монтировании вызывает session.restore().
Вопрос: Что будет, если не вернуть cleanup из эффекта с подпиской?
Ответ: Подписка переживёт компонент: колбэк продолжит вызываться и писать в стор или state размонтированного компонента. Это утечка памяти и лишние запросы.

5Рендеринг: Virtual DOM, reconciliation, условный рендеринг

React строит лёгкое описание интерфейса, сравнивает его с прошлым и меняет в DOM только разницу.

Определение. Virtual DOM - дерево обычных JS-объектов, описывающее интерфейс. Его дёшево создавать заново на каждый рендер, в отличие от настоящего DOM.
Определение. Reconciliation (согласование) - алгоритм сравнения нового виртуального дерева со старым. По его результату React вносит минимальный набор изменений в реальный DOM (этап commit).

Упрощения, благодаря которым сравнение линейное, а не кубическое:

  • если у узла сменился тип (div на span, один компонент на другой), поддерево пересоздаётся целиком;
  • элементы списка сопоставляются по key. Ключ должен быть стабильным и уникальным (id), не индекс массива.

Условный рендеринг

{loading && <Spinner />}                         // показать или ничего
{error ? <Alert>{error}</Alert> : <Table />}       // одно из двух
if (restoring) return <p>вспоминаем...</p>;      // ранний return
Ловушка. {count && ...} при count === 0 выведет на экран "0". Безопаснее {count > 0 && ...}.
В нашем коде. В таблице студентов key={student.isuId}. В App.jsx компонент StudentRoute рендерит <StudentDetailsPage key={isuId} />: при переходе к другому студенту меняется key, и React создаёт компонент заново с чистым состоянием вместо того, чтобы переиспользовать старый.
Вопрос: Почему плохо использовать индекс массива как key?
Ответ: При удалении или сортировке индексы сдвигаются, и React сопоставит не те элементы: состояние и DOM одной строки достанутся другой, плюс лишние перерисовки.

6Реактивность во frontend

Реактивность - автоматическое обновление зависимых значений и интерфейса, когда меняются исходные данные.

Определение. Реактивность - модель, где мы описываем зависимости ("таблица зависит от списка студентов"), а система сама пересчитывает зависимое при изменении источника. Как формула в Excel.

Ловушка. В React состояние неизменяемо. state.items.push(x) не вызовет перерисовку: ссылка на массив та же. Надо создать новый объект: setItems([...items, x]).
В нашем коде. Три уровня реактивности: useState в компонентах, zustand-сторы (useStore(sessionStore) перерисовывает компонент при изменении сессии) и RxJS-потоки, которые реагируют на смену запроса, видимость вкладки и изменения студентов. В writeResource стор обновляется через новые объекты ({ ...current, ...patch }).
Вопрос: Почему React называют "не по-настоящему реактивным"?
Ответ: Он не отслеживает зависимости автоматически: перерисовка запускается явным setState, а затем React перерисовывает всё поддерево и сравнивает. Vue и сигналы знают точно, что от чего зависит.

7Управление состоянием: локальное и глобальное

Правило: держать состояние как можно ближе к месту, где оно используется, и поднимать выше только когда оно нужно многим.

Определение. Локальное состояние принадлежит одному компоненту (useState): открыта ли модалка, идёт ли отправка формы, текст ошибки.
Определение. Глобальное состояние нужно многим несвязанным компонентам: кто вошёл, его токен и роль, кешированные данные.
инструментособенности
Context APIвстроен в React; подходит для редко меняющихся данных; при изменении перерисовывает всех потребителей
Redux Toolkitединый стор, изменения только через actions и reducers; предсказуемо, много шаблонного кода, хорошие devtools
Zustandмаленький стор-хук без провайдеров; подписка на часть состояния через селекторы

Полезно различать: серверное состояние (кеш данных с бэкенда, может устареть) и клиентское (UI). Для серверного часто берут React Query или SWR; у нас эту роль играют RxJS-поток и studentsStore.

В нашем коде. Zustand, сторы созданы через createStore из zustand/vanilla, чтобы их можно было читать и вне React (сервис сессии, RxJS):
sessionStore: tokens, user, restoring, сообщения, счётчик generation.
studentsStore: resources - результаты запросов по ключу (loading, data, error).
Локальное: submitting, message, showConfirm, текущие фильтры и страница в StudentsPage.
Вопрос: Почему токен в глобальном состоянии, а флаг отправки формы - в локальном?
Ответ: Токен и пользователь нужны навигации, защите маршрутов, HTTP-клиенту и страницам. Флаг отправки нужен только самой форме и умирает вместе с ней.

8Реактивное программирование и императивный подход

Императивно - пошагово говорим "что сделать". Реактивно - объявляем, как одни потоки данных получаются из других.

Определение. Императивный стиль: последовательность команд, явно меняющих состояние. "Когда пользователь ввёл символ, сбрось таймер, через 300 мс отправь запрос, отмени прошлый, запиши результат".
Определение. Реактивное программирование: работа с асинхронными потоками событий. Результат описывается как преобразование потока: "поток запросов = поток ввода, с паузой 300 мс, без повторов, с отменой устаревшего".

Одна задача двумя способами

// императивно
let timer, controller;
input.oninput = () => {
  clearTimeout(timer);
  timer = setTimeout(async () => {
    controller?.abort();
    controller = new AbortController();
    render(await load(input.value, controller.signal));
  }, 300);
};

// реактивно
fromEvent(input, 'input').pipe(
  map(e => e.target.value),
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => requestObservable(signal => load(q, signal))),
).subscribe(render);

Реактивный вариант короче, отмена и порядок ответов получаются "бесплатно", а куски цепочки легко переиспользовать. Минус: нужен порог входа и отладка сложнее.

В нашем коде. Вся логика "когда загружать студентов" вынесена из компонентов в features/students/resourceStream.js. Компонент только отдаёт запрос в поток и рисует результат.
Вопрос: Когда реактивный подход избыточен?
Ответ: Для одиночных действий без комбинирования событий: нажали кнопку, отправили форму, получили ответ. Там хватает async/await.

9RxJS: Observable, Observer, Subject, BehaviorSubject, Subscription

Observable - это "функция, которая может вернуть много значений во времени", ленивая до подписки.

Определение. Observable - источник значений во времени. Может выдать сколько угодно next, затем завершиться complete или упасть error. Ленив: ничего не делает, пока на него не подписались.
Определение. Observer - объект с методами next, error, complete, который получает значения.
Определение. Subscription - результат subscribe(). Метод unsubscribe() прекращает получение значений и вызывает teardown-функцию источника.
Определение. Subject - одновременно Observable и Observer: в него можно вручную вызвать next(), и значение получат все текущие подписчики (multicast).
вид Subjectчто получает новый подписчик
Subjectтолько будущие значения
BehaviorSubject(initial)сразу текущее значение, потом будущие; есть .value
ReplaySubject(n)последние n значений
AsyncSubjectтолько последнее значение после complete
В нашем коде.
requestObservable(load) - свой Observable: при подписке запускает запрос с AbortController, а teardown (return () => controller.abort()) отменяет запрос при отписке.
studentChanges = new Subject() в studentEvents.js: после успешного создания, изменения или удаления studentActions.js вызывает studentChanges.next(isuId), и все открытые списки перезагружаются.
query$ = new BehaviorSubject(query) в useStudentResource: хранит текущий запрос, новый подписчик сразу его получает.
active$ - Observable поверх sessionStore.subscribe: превращает изменения стора в поток.
Вопрос: Почему для query$ BehaviorSubject, а не Subject?
Ответ: Поток подписывается на query$ позже, чем мы туда положили первый запрос. Subject это значение потерял бы, BehaviorSubject отдаёт текущее значение новому подписчику.
Вопрос: Чем Observable отличается от Promise?
Ответ: Promise - одно значение, запускается сразу, не отменяется. Observable - много значений, ленивый (стартует при подписке), отменяется через unsubscribe.

В нашем коде (resourceStream.js):
active$.pipe(distinctUntilChanged(), switchMap(observeSession)) - при выходе из аккаунта весь поток загрузок отменяется.
query$.pipe(distinctUntilChanged(sameQuery), switchMap(observeQuery)) - одинаковые запросы не повторяются, новый запрос отменяет старый.
timer(delay) - задержка 300 мс только при смене ФИО (свой debounce).
merge(timer(0, pollInterval), changes$).pipe(exhaustMap(...)) - опрос каждые 5 секунд плюс внеочередная загрузка после изменений, без наложения запросов.
visible$.pipe(switchMap(...)) - на скрытой вкладке опрос останавливается (EMPTY).
map, catchError, startWith({ kind: 'loading' }) - превращают запрос в события loading, data, error.
Вопрос: Почему для опроса exhaustMap, а не switchMap?
Ответ: Если сервер отвечает дольше интервала, switchMap отменял бы каждый запрос и данные никогда бы не пришли. exhaustMap дожидается текущего запроса и пропускает тики, пришедшие в это время.
Вопрос: Зачем catchError внутри switchMap, а не в конце цепочки?
Ответ: Ошибка завершает поток. Если поймать её в конце, весь внешний поток умрёт и опрос прекратится. Внутри switchMap умирает только один запрос, а ошибка превращается в событие { kind: 'error' }.

11Асинхронные потоки: hot и cold, подписки, утечки памяти

Определение. Cold Observable создаёт источник заново для каждого подписчика. Два подписчика на HTTP-запрос - два запроса.
Определение. Hot Observable имеет общий источник, который существует независимо от подписчиков. Опоздавший подписчик пропустит прошлые значения. Примеры: события DOM, Subject.

Холодный поток делают горячим (общим) операторами share() и shareReplay().

Утечки памяти

Подписка держит ссылки на колбэки, а через них на компоненты. Если не отписаться, компонент не соберётся сборщиком мусора, а колбэк продолжит работать: таймеры тикают, запросы идут.

  • отписываться в cleanup useEffect;
  • использовать операторы, которые сами завершают поток: take, takeUntil, switchMap (отписывается от старого);
  • в teardown собственного Observable освобождать ресурсы.
В нашем коде. requestObservable - холодный: каждый подписчик запускает свой запрос. studentChanges (Subject) и fromEvent(document, 'visibilitychange') - горячие. В useStudentResource cleanup эффекта делает subscription.unsubscribe(): отписка проходит по всей цепочке, switchMap отписывается от внутренних потоков, и teardown requestObservable вызывает controller.abort(). Таймер опроса тоже останавливается.
Вопрос: Таймер опроса и fromEvent - это утечка, если уйти со страницы?
Ответ: Нет, если отписаться: unsubscribe убирает обработчик visibilitychange и останавливает timer. Утечка была бы, если бы подписку не сохранили и не отменили в cleanup.

12Реактивная обработка событий: поиск, фильтрация, отмена устаревших запросов

Три проблемы живого поиска

  1. Слишком много запросов: запрос на каждую букву. Решение: debounce, ждать паузу во вводе.
  2. Повторы: тот же запрос ещё раз. Решение: distinctUntilChanged.
  3. Гонка ответов (race condition): ответ на старый запрос "Ива" пришёл после ответа на "Иван" и перезаписал его. Решение: switchMap отменяет устаревший запрос.

Наш поток

query$ (BehaviorSubject: фильтры, ФИО, сортировка, страница)
  -> distinctUntilChanged(sameQuery)        без повторов
  -> switchMap(query =>
       timer(ФИО изменилось ? 300 : 0)      debounce только для ввода текста
       -> switchMap(опрос: каждые 5 с + studentChanges)
            -> exhaustMap(запрос с AbortController)
     )

Как отменяется запрос

Когда приходит новый запрос, switchMap отписывается от предыдущего внутреннего потока. Отписка вызывает teardown requestObservable, тот вызывает controller.abort(), и fetch обрывается с AbortError. Сеть освобождается, а старый ответ точно не попадёт в интерфейс.

В нашем коде. Фильтры в StudentsPage - состояние; через useMemo собирается объект запроса и отдаётся в useStudentList, а тот кладёт его в query$.next(query). При смене фильтров страница сбрасывается на 1.
Вопрос: Что такое race condition в поиске?
Ответ: Ответы приходят не в том порядке, в котором ушли запросы, и старый результат перезаписывает новый. switchMap игнорирует и отменяет всё, кроме последнего запроса.

13Клиентская валидация, обработка ошибок, состояния загрузки

Валидация

Клиентская валидация - для удобства: ошибка видна сразу, без запроса. Защищает данные только серверная валидация, потому что клиент можно обойти.

  • HTML-атрибуты: required, min, max, minLength, pattern, type="email". Браузер не даст отправить форму (Constraint Validation API).
  • Проверка в JS перед отправкой: studentDto() и searchDto() в domain/student.js повторяют правила бэкенда (ИСУ 6 цифр, группа [A-Z][0-9]{4}, дата не раньше 2000-01-01, длина ФИО 5-100).

14Аутентификация и авторизация. JWT, access и refresh

Определение. Аутентификация - проверка, кто ты (логин и пароль). Авторизация - проверка, что тебе можно (роль USER или ADMIN).
Определение. JWT (JSON Web Token) - строка header.payload.signature в base64url. Payload содержит claims: sub (логин), roles, exp (срок), iss, aud. Подпись (у нас HS256) позволяет серверу проверить, что токен не подделан, без обращения к базе.
Ловушка. JWT подписан, но не зашифрован. Payload читается кем угодно, поэтому секретов туда не кладут.

Access и refresh

accessrefresh
зачемприкладывается к каждому запросу в Authorization: Bearer ...только чтобы получить новую пару
сроккороткий, 15 минутдлинный, 7 дней

Короткий access ограничивает ущерб от утечки, refresh позволяет не вводить пароль каждые 15 минут. При каждом обновлении выдаётся новый refresh, старый отзывается (rotation).

В нашем коде.
Access-токен хранится только в памяти (sessionStore), не в localStorage.
Refresh-токен бэкенд кладёт в cookie lab4_refresh: HttpOnly (JS не прочитает), SameSite=Strict, Path=/api/auth/session (уходит только на эндпоинты сессии).
При старте session.restore() вызывает /api/auth/session/refresh и восстанавливает вход после F5.
authorizedClient на 401 делает один refresh и повторяет запрос. sessionService не допускает двух параллельных refresh (общий promise), а счётчик generation отбрасывает ответы, пришедшие после выхода или смены пользователя.
Роль для интерфейса берётся из payload через userFromToken().
Вопрос: Почему access не в localStorage?
Ответ: localStorage доступен любому скрипту на странице: при XSS токен украдут. В памяти он живёт до перезагрузки, а восстанавливается через HttpOnly refresh-cookie, недоступную JS.
Вопрос: Как сделать выход, если JWT нельзя отозвать?
Ответ: Отозвать refresh в БД и забыть access на клиенте. Украденный access проживёт максимум до своего exp, поэтому он короткий.

15Защита маршрутов и разграничение доступа по ролям

Клиентская защита - это UX, настоящая защита на сервере.

  • Охрана маршрута: компонент-обёртка проверяет сессию и роль до рендера страницы, иначе перенаправляет на вход или показывает "нет прав".
  • Скрытие элементов: кнопки, которые пользователю недоступны, не рендерятся.
  • Сервер проверяет роль на каждом запросе. Даже если кто-то вручную вызовет DELETE, Spring Security вернёт 403.
В нашем коде. ProtectedRoute: пока сессия восстанавливается - "вспоминаем, кто зашёл..."; нет токена - <Navigate to="/login" replace />; adminOnly и роль не ADMIN - "у миня нет прав". Только для админа: /students/new и /students/:isuId/edit. В Navigation, StudentsPage, StudentDetailsPage кнопки создания, изменения и удаления показываются при user.role === 'ADMIN'. В SecurityConfig бэкенда: GET студентов - USER и ADMIN, POST, PATCH, DELETE - только ADMIN.
Вопрос: Достаточно ли спрятать кнопку "Удалить" от USER?
Ответ: Нет. Запрос можно отправить вручную с токеном USER. Защищает проверка роли на сервере, скрытие кнопки только убирает лишнее из интерфейса.
Вопрос: Зачем replace в Navigate?
Ответ: Чтобы защищённый адрес не остался в истории: иначе кнопка "назад" со страницы входа снова отправит на защищённую страницу и опять на вход.

16Безопасность frontend: XSS, CSRF

Определение. XSS (Cross-Site Scripting) - внедрение чужого скрипта на страницу: например, в поле "примечания" сохранили <img src=x onerror=...>, и он выполнился у другого пользователя. Скрипт работает от имени жертвы: читает токены, шлёт запросы.

Защита от XSS:

  • экранирование вывода: React по умолчанию выводит {text} как текст, а не как HTML;
  • не использовать dangerouslySetInnerHTML и innerHTML с пользовательскими данными;
  • не хранить токены там, где их достанет JS (localStorage); HttpOnly cookie;
  • Content-Security-Policy запрещает инлайновые и чужие скрипты.
Определение. CSRF (Cross-Site Request Forgery) - чужой сайт заставляет браузер жертвы отправить запрос на наш сайт. Браузер сам приложит cookie, и запрос пройдёт от имени жертвы.

Защита от CSRF:

  • SameSite=Strict или Lax у cookie: браузер не отправит её с запросом с чужого сайта;
  • CSRF-токен или обязательный кастомный заголовок: чужой сайт не может добавить заголовок к запросу без разрешения CORS;
  • проверка заголовков Origin и Referer.

Связь: при авторизации через заголовок Authorization CSRF не страшен (чужой сайт не знает токен), но страшен XSS. При cookie наоборот. Поэтому мы комбинируем.

В нашем коде. Нигде нет dangerouslySetInnerHTML, примечания выводятся как текст. Access в памяти и уходит в заголовке. Refresh-cookie: HttpOnly + SameSite=Strict + узкий Path. Бэкенд требует заголовок X-Requested-With: XMLHttpRequest на /api/auth/session/*, иначе 403 FORBIDDEN_REQUEST. CORS разрешает только наши origin и не разрешает credentials для чужих сайтов.
Вопрос: Почему кастомный заголовок защищает от CSRF?
Ответ: HTML-форма или картинка с чужого сайта не может добавить заголовок, а fetch с нестандартным заголовком на другой origin требует preflight, который наш CORS не пропустит.

18Docker: Dockerfile, образы, контейнеры

19Многоэтапная сборка и раздача статики через Nginx

Собираем в одном образе, запускаем в другом. В итоговый образ попадает только результат.

FROM node:22-alpine AS build        # этап 1: есть node и все dev-зависимости
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build                   # vite собирает dist/

FROM nginx:stable-alpine            # этап 2: только nginx и готовая статика
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist/ /usr/share/nginx/html/

Зачем: итоговый образ весит десятки мегабайт вместо сотен, в нём нет исходников, node_modules и инструментов сборки, меньше поверхность атаки.

После vite build React-приложение - это просто статические файлы (HTML, JS, CSS). Для них не нужен Node: достаточно веб-сервера.

Nginx у нас делает две вещи

location /api/ { proxy_pass http://backend:8080; }   # reverse proxy на Java
location /     { try_files $uri $uri/ /index.html; } # SPA fallback

Проксирование /api даёт один origin для фронта и API: не нужен CORS, cookie работают как first-party, а SameSite=Strict не мешает. В разработке ту же роль играет server.proxy в vite.config.js.

Вопрос: Что даёт proxy_pass по сравнению с прямым запросом браузера на :8080?
Ответ: Один origin: нет CORS и preflight, cookie сессии отправляются автоматически, бэкенд можно не открывать наружу, адрес бэкенда не зашит во фронт.

20Docker Compose: сети, переменные окружения, связь frontend и backend

Определение. Docker Compose описывает несколько контейнеров одного приложения в docker-compose.yml и поднимает их одной командой docker compose up --build.
  • Сеть: compose создаёт общую сеть, и контейнеры находят друг друга по имени сервиса (встроенный DNS). Поэтому в nginx адрес http://backend:8080, а в бэкенде jdbc:postgresql://db:5432/students.
  • ports: проброс порта наружу, "127.0.0.1:8081:80" - только для локальной машины.
  • depends_on с condition: service_healthy: бэкенд стартует после того, как healthcheck базы (pg_isready) прошёл.
  • volumes: postgres_data хранит базу между перезапусками; SQL-скрипты из docker-entrypoint-initdb.d выполняются при первом создании базы.
  • Переменные окружения: секреты в .env (в git не попадает), пример в .env.example. ${DB_PASSWORD:?...} - обязательная переменная, без неё compose не запустится; ${COOKIE_SECURE:-false} - значение по умолчанию.
Ловушка. Пароль базы применяется только при первом создании тома. Сменили DB_PASSWORD - нужно docker compose down -v, иначе "password authentication failed".
Ловушка. Переменные VITE_* подставляются в код при сборке, а не при запуске контейнера: статике неоткуда читать окружение в рантайме.
В нашем коде. Три сервиса: db (postgres:17-alpine), backend (Spring Boot), frontend (nginx со статикой). Браузер ходит на localhost:8081, nginx проксирует /api в backend:8080.
Вопрос: Почему в nginx.conf написано backend, а не localhost?
Ответ: localhost внутри контейнера - это сам контейнер nginx. Бэкенд в другом контейнере, и в сети compose он доступен по имени сервиса.

Шпаргалка к защите

Вопрос: Расскажи про приложение за минуту.
Ответ: SPA на React 19 + Vite. Маршруты react-router, вёрстка react-bootstrap. Глобальное состояние в zustand: сессия и кеш загрузок. Загрузка студентов - RxJS-поток с debounce поиска, отменой устаревших запросов, опросом раз в 5 секунд и паузой на скрытой вкладке. JWT: access в памяти, refresh в HttpOnly cookie. В Docker три контейнера: Postgres, Spring Boot и nginx, который раздаёт статику и проксирует /api.
Вопрос: Где у вас RxJS и почему не просто useEffect?
Ответ: features/students/resourceStream.js. Там сочетаются несколько источников: смена запроса, таймер опроса, видимость вкладки, изменения после CRUD и сессия. Через switchMap, exhaustMap и merge это описывается декларативно и с правильной отменой; на useEffect вышла бы гора таймеров и флагов.
Вопрос: Как список узнаёт, что студента удалили на другой странице?
Ответ: deleteStudent после ответа сервера делает studentChanges.next(id). Поток списка слушает studentChanges через merge и внепланово перезагружается.
Вопрос: Что будет при истечении access-токена посреди работы?
Ответ: Запрос вернёт 401, authorizedClient вызовет session.refresh (один на всех ожидающих), получит новый access через cookie и повторит запрос. Если refresh тоже истёк - сессия очищается и показывается "Сессия истекла".
Вопрос: Как защищены от XSS и CSRF?
Ответ: XSS: React экранирует вывод, нет dangerouslySetInnerHTML, access не в localStorage, refresh HttpOnly. CSRF: refresh-cookie SameSite=Strict с узким Path, обязательный X-Requested-With на эндпоинтах сессии, остальные запросы с Bearer-заголовком.
Вопрос: Зачем multi-stage build?
Ответ: Node и зависимости нужны только для сборки. В финальный образ попадают nginx и папка dist: он маленький и без лишнего.
